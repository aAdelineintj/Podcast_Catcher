### 为什么放弃多租户路线（2026-09-16）

在完成成本测算后发现，公开推广的代价远超预期：

1. **成本线性增长且不可控**：1 万用户规模约 2.6 万元/月，且随用户增长无上限。
2. **匿名身份存在结构性滥用漏洞**：匿名用户清缓存即可重置身份，无限领取免费额度。
   堵住它需要「匿名只读 + 注册才可上传」，等于把产品体验砍掉一半。
3. **大量非核心工作量**：账号体系、配额系统、隐私政策、用户协议、人机验证、
   内容合规——这些都与「播客精听」这个核心价值无关。

**结论**：单用户场景下这些问题全部不存在，且成本为 0。

### 为什么把数据搬上云（2026-09-19）

旧架构把历史记录与收藏存在浏览器 `localStorage` 里。它有一个致命缺陷：
**关掉浏览器、重启电脑还在，但换浏览器、清缓存、换设备、重装系统就全没了。**

修好它不需要回到多租户路线——因为数据只属于一个人：

- 不需要账号体系、配额、多租户隔离（这些仍然**不做**）
- 用 Supabase 免费版 Postgres + Storage 承载，成本仍是 **0 元**
- 前端仍然可以只跑在 Vercel 免费版上

## 2. 仍然存在的问题（自用视角）

### 2.1 翻译串行等待 —— 结论修正：它不是瓶颈

本文件旧版本写道「一集 12.5 分钟 = 184 句 = 至少 184 秒纯等待」。
**那个估算与代码不符**：它假设「一句一次请求」，而现有实现
`baidu_translate_batch` 是**换行符一次提交多段**（`TRANSLATE_BATCH_CHARS=1500`），
并按 `TRANSLATE_QPS` 令牌桶限速、`TRANSLATE_MAX_WORKERS` 并发。

按真实实现重算：

| 场景 | 批次 | 耗时 |
|---|---|---|
| 30 分钟播客（约 20,900 字符） | ≈ 14 批 | 标准版 QPS=1 → **约 14 秒**；高级版 QPS=10 + 6 并发 → **约 2 秒** |

**结论：不需要为它做任何架构改动。**
唯一可选优化是实名升级百度翻译高级版（免费额度 200 万字符/月，QPS=10）。

### 2.2 公网暴露风险 —— 三层防护

服务部署在公网，且服务端持有付费 API key。**公网上任何无鉴权的、带密钥的服务都会被扫描到。**

| # | 层 | 状态 |
|---|---|---|
| ① | **口令闸门**：`src/proxy.ts` 拦截页面与 `/api/*`，未登录返回 401 / 跳登录页；`PASSPHRASE` + `AUTH_SECRET` 任一为空则 **fail-closed 整站 503** | ✅ 已落地 |
| ② | **浏览器端不使用 anon key**：所有 DB 读写走 Next Route Handlers，用 `SUPABASE_SERVICE_ROLE_KEY`（仅服务端环境变量，**不加 `NEXT_PUBLIC_` 前缀**） | ✅ 已落地 |
| ③ | **RLS 开启 + 零策略**（anon key 即使泄露也读不到任何一行）+ 私有 bucket + 服务端现签 signed URL | ✅ 已落地 |

推论：`NEXT_PUBLIC_SUPABASE_ANON_KEY` 这个变量在本项目**根本不需要存在**。

### 2.3 仓库冗余 —— 已从「顺手做」升级为「push 前置条件」

`.gitignore` 维护良好（`venv/`、`node_modules/`、`data/input/*`、`data/output/*`、
`data/jobs/` 均已排除），但根目录仍有**不该被跟踪的文件**，其中 `006.mp3` 达 **17 MB**：

```

```

因为上云必须 push 到 GitHub，这一步现在是**硬前置**，不再是可选优化。

## 3. 实测数据

### 3.1 Whisper 选型实测

测试素材：874.3 秒法语播客，M1 CPU，`WHISPER_BILINGUAL=0`。

| 配置 | 耗时 | 实时倍率 | 行数 | 句粒度中位 | p90 |
|---|---|---|---|---|---|
| `base` 单遍 | 88.7s | 9.9× | 205 | 2.4s | 5.4s |
| `base` 双遍裁决 | 157.0s | 5.6× | 207 | 2.3s | 5.5s |
| **`small` 单遍** | **234.7s** | **3.7×** | 195 | 2.5s | 5.6s |

**`small` 胜出**，它修好了 `base` 的每一类错误：

- `parler des loiscires` → `parler des loisirs`
- `Léger times activities` → `Leisure time activities, our likes and dislikes, I suppose you could say.`
- 整句丢失的 `Cela permet d'apprendre de nouvelles choses tout en se détendant.` 完整还原
- 中文译文从「我们来谈谈**洛伊斯**」变成「我们要谈谈**爱好**」

**双遍裁决不划算**：逐行 diff 仅 13/205 行有实质差异（多数只是断句边界位移），
却要多花 1.77× 时间 → 默认关闭（`WHISPER_BILINGUAL=0`）。

### 3.2 句粒度落在精听可用区间

中位 2.5s / p90 5.6s。三重二次切句规则（`whisper_asr._split_to_sentences`）：
句末标点 / 词间静音 ≥0.6s / 时长 ≥12s 或字数 ≥180。

### 3.3 自用场景成本：0 元

| 项 | 免费额度 | 折算 |
|---|---|---|
| ASR | 本机 Whisper，**无额度限制** | 0 元 |

## 5. 表结构（Supabase，阶段二执行）

> 本节替换旧版「表结构（已废弃）」。旧版的多租户设计
> （`users` / `usage` / `ip_usage`）**确认不再需要**，不要恢复。

四张表 + 两个 RPC：

| 对象 | 承载 | 要点 |
|---|---|---|
| `podcasts` | `StoredPodcast` + worker 认领状态 | `status` ∈ `queued/processing/success/failed`；`audio_path`、`audio_uploaded_at`、`locked_by`、`locked_at`、`attempts`；`updated_at` 触发器 |
| `segments` | `TranscriptSegment` | `(podcast_id, idx)` 唯一；同时存 `start_label`（`"M:SS"`）与 `start_seconds`（数值，用于排序与跳转） |
| `favorites` | `FavoriteSentence` | `id text primary key` 沿用 `buildFavoriteId = ${podcastId}:${start}`；`tags text[]` |
| `worker_heartbeat` | 前端显示「worker 在线/离线」 | worker 每 5s upsert 一次，兼作 **Supabase 保活**（防免费项目 7 天无活动休眠） |
| `claim_next_podcast(worker_id)` | **原子认领** | `FOR UPDATE SKIP LOCKED`；`locked_at < now() - 30min` 视为租约超时可重抢；要求 `audio_uploaded_at is not null` |
| `touch_worker(...)` | 心跳 upsert | — |

### 5.1 音频不经 Vercel（绕开 4.5MB 请求体上限）

播客 mp3 常 20–100MB，远超 Vercel Serverless Function 的 4.5MB 上限。
**大文件从不经过 Vercel 函数**，走浏览器直传 Storage：

```
浏览器                    Vercel Route Handler            Supabase
  │ POST /api/podcasts ──────▶│ insert podcasts(status=queued)
  │                           │ POST /storage/v1/object/upload/sign/... (service_role)
  │ ◀─ {podcastId,uploadUrl} ─│
  │ PUT uploadUrl (原始字节 20~100MB) ───────────────────▶ Storage
  │ POST /api/podcasts/{id}/uploaded ─▶│ set audio_uploaded_at=now()
  │ router.push(`/podcast/{id}`)
```

元数据在**签发时**就建好行（`status=queued`，`audio_uploaded_at` 为空）；
`claim_next_podcast` 要求 `audio_uploaded_at is not null`，
所以**上传中断的任务永远不会被 worker 误领**。

### 5.2 权限

RLS 开启 + **零策略**；所有读写经 Route Handlers 用 `SUPABASE_SERVICE_ROLE_KEY`
（service_role 绕过 RLS）；音频走私有 bucket + 服务端现签 signed URL。
详见 §2.2。

## 6. 阶段二踩到的坑（2026-09-20）

> 这一节全是**只有真跑一次才会暴露**的问题：静态检查、单元自检、官方文档都没拦住它们。
> 记下来是因为每一个的症状都指向错误的方向。

### 6.1 Storage 两个签名端点的响应字段名不一致

| 端点 | 响应字段 |
|---|---|
| `POST /storage/v1/object/upload/sign/{bucket}/{path}` | **`url`**（另有 `token`） |
| `POST /storage/v1/object/sign/{bucket}/{path}` | **`signedURL`**（URL 三个字母大写） |

写错字段名**不会抛错**，只会拿到 `undefined` —— 表现是上传或播放静默失败，
而错误信息完全指不到原因。已用 `e2e_cloud probe-storage` 把真实响应钉死。

附带一条：**上传签名 URL 的过期时间固定 2 小时，不可配置**，传 `expiresIn` 无效。
实际影响不大（签发后前端立刻上传），但别指望能调它。

### 6.2 DELETE 带 JSON 的 Content-Type 但空 body → Fastify 400

Storage 的 DELETE 端点是 Fastify 实现的，看到 `Content-Type: application/json`
却没有 body 时直接拒绝：

```
400 {"statusCode":400,"error":"FastifyError",
     "message":"Body cannot be empty when content-type is set to 'application/json'"}
```

后果比看上去严重：worker 压缩音频后删不掉原始大文件、Route Handler 删播客时音频删不掉。
而这两处的删除失败都是**刻意只打警告不中断**的（不该因为清不掉音频就不让用户删记录），
所以问题会静默地堆积孤儿文件，直到某天 Storage 配额满了才发现。

修法：**只在真有请求体时才加 Content-Type**。Python（`supabase_client.py`）与
TypeScript（`supabase-server.ts`）两侧都改了。

### 6.3 `beforeFiles` rewrite 会遮蔽 Route Handlers

`next.config.ts` 用的是 `beforeFiles`，它跑在**文件系统路由之前**。
原先那条 `/api/:path*` → FastAPI 的转发，会让 `src/app/api/**` 下所有 Route Handler
永远不执行 —— 表现是线上 `/api/*` 全 500，而 Next 不会给任何「路由被遮蔽」的提示。

修法：FastAPI 的转发只用**不带 `/api` 前缀的根路径**。
`backend/main.py` 本来就把同一个 router 同时挂在 `/api` 和根路径两处，功能完全等价，
所以 `/api/*` 可以整个让给 Route Handlers。

### 6.4 Next 的类型产物会滞后，导致 `tsc` 报假错误

新增 Route Handler 之后 `npx tsc --noEmit` 报：

```
.next/types/validator.ts(24,44): error TS2344: Type 'Route' does not satisfy the constraint 'never'.
```

这不是代码错，而是 `.next/types/routes.d.ts` 还是旧的（里面的 rewrite 列表甚至还是改配置之前的）。
**dev server 打印 `✓ Ready in 61s` 也不代表它重新生成了类型** —— 那句话只表示端口在监听。

修法：删掉 `.next/types` 再跑 `tsc`；Next 会在下次 build 时重新生成正确版本。

### 6.5 PostgREST 的 JSON body 里 `now()` 不是 SQL 函数

`{"audio_uploaded_at": "now()"}` 不会在服务端求值。PostgREST 走的是值绑定，
字符串就是字符串（或者直接类型报错）。要服务端时间必须传 ISO 时间戳，
且统一用 UTC —— 用本机时区写会把时间写歪，而 Supabase 存的是 `timestamptz`，
歪掉的偏移量在界面上看不出来。

### 6.6 `favorites.podcast_id` 的级联删除与「冗余 title」自相矛盾

初版外键写的是 `on delete cascade`，但同一行的注释写着
「冗余一份 podcast_title：播客被删后收藏仍可读」—— cascade 会把整行删掉，
冗余字段完全失去意义。两个设计意图互相抵消。

改成 `on delete set null`：播客被删后收藏保留、`podcast_id` 置 NULL，
冗余标题此时才真正派上用场。同时收藏列表联查 `podcasts(title)` 取**实时**标题，
于是「改播客名 → 收藏夹跟着变」和「播客被删 → 收藏仍显示快照名」两件事都能成立。

> 已建过表的库要单独跑 `alter table` —— `create table if not exists` 遇到已存在的表会整段跳过，
> 包括外键定义。见 `supabase/schema.sql` favorites 段后的 ALTER 语句。

### 6.7 用本机时钟去减数据库时钟 → 算出负数

`/api/health` 早期返回 `"ageSeconds": -1`，前端会显示「最后心跳 -1 秒前」。

根因不是逻辑写错，而是**两个时钟源混用**：

| 环节 | 时钟来源 |
| --- | --- |
| 写入 `worker_heartbeat.last_seen` | SQL 函数 `touch_worker` 里的 `now()`（Supabase 服务器） |
| 读取并计算 age（`/api/health`） | `Date.now()`（用户本机） |

两台机器的时钟不可能完全一致。实测（只读采样 45 次 / 间隔 0.4s）：

```
age 最小值     -1.507s
age 最大值     +3.774s
负值样本       14 / 45
→ 服务端时钟比本机快约 1.5s
```

JS 侧 `Math.round(ageMs / 1000)` 在 `age ∈ [-1.5s, -0.5s)` 时正好得到 `-1`，
所以 14/45 的采样都会显示成负数。

修法：`Math.max(0, Math.round(ageMs / 1000))`。

> **这类 bug 的通用识别特征**：只要「写入时间」和「比较时间」不是同一个时钟源，
> 就一定会有偏移。此时任何「时间差」字段都应该默认 clamp 到合法区间，
> 而不是假设它天然非负。判断 worker 是否在线（`ageMs < 30_000`）也会被偏移影响，
> 只是 δ≈1.5s 相对于 30s 窗口可以忽略。
